# АИС «Цифровой университетский архив»

Практическая работа №5 по теме:

**«Проектирование стратегии ветвления Git Flow для распределенной команды разработки»**

Проект представляет собой пример организации разработки модуля шифрования файлов для АИС «Цифровой университетский архив» с использованием модели ветвления Git Flow.

## Основная часть

В проекте используется стратегия Git Flow с разделением веток по их назначению.

Основные ветки репозитория:

- `main` — содержит стабильные релизные версии проекта;
- `develop` — используется как основная интеграционная ветка;
- `feature/crypto-module` — предназначена для разработки модуля шифрования файлов;
- `release/1.0.0` — используется для подготовки и стабилизации первого релиза;
- `hotfix/1.0.1` — предназначена для экстренного исправления ошибки после выпуска стабильной версии.

Для стабильных версий проекта используются теги:

- `v1.0.0` — первый стабильный релиз;
- `v1.0.1` — версия после экстренного исправления.

### Разработка модуля шифрования

Разработка нового функционала выполнялась в ветке `feature/crypto-module`.

В этой ветке был создан консольный проект на .NET 8 и реализован класс `FileEncryptionService`.

Модуль использует пространство имен `System.Security.Cryptography` и алгоритм AES для шифрования файлов.

В процессе разработки были выполнены следующие коммиты:

- `Add initial file encryption module`
- `Add source file validation`
- `Add path validation to encryption service`

После завершения разработки ветка `feature/crypto-module` была объединена с `develop`.

### Интеграционное тестирование

После включения модуля шифрования в `develop` был предусмотрен этап интеграционного тестирования.

На данном этапе проверялись:

- корректность работы модуля шифрования;
- взаимодействие с другими частями системы;
- обработка некорректных путей;
- работа с отсутствующими файлами;
- стабильность приложения;
- отсутствие критических ошибок.

После завершения тестирования была создана ветка `release/1.0.0`, в которой выполнялась подготовка стабильной версии к выпуску.

### Выпуск стабильной версии

После завершения стабилизации ветка `release/1.0.0` была объединена с `main`.

Для первой стабильной версии был создан тег `v1.0.0`.

Изменения из `release/1.0.0` также были возвращены в `develop`, чтобы все исправления сохранились в дальнейшей разработке.

### Экстренное исправление

После выпуска версии `v1.0.0` был смоделирован сценарий обнаружения критической ошибки при работе с файлами.

Для ее исправления была создана ветка `hotfix/1.0.1`.

В модуль была добавлена обработка исключений `IOException` и `UnauthorizedAccessException`.

После исправления ветка `hotfix/1.0.1` была объединена с `main` и `develop`.

Новая стабильная версия была отмечена тегом `v1.0.1`.

## Схема Git Flow

```text
GitFlow-Lifecycle/
|
├── main (Стабильная версия системы)
|   ├── [Релиз v1.0.0] <------------------------------------┐
|   └── [Hotfix v1.0.1] <-------------------------------┐   |
|                                                       |   |
├── develop (Основная ветка интеграции кода)            |   |
|   ├── [Слияние] feature/crypto-module --------------> |   |
|   ├── [Интеграционное тестирование]                   |   |
|   └── [Слияние] release/1.0.0 ------------------------┘   |
|                                                           |
├── feature/ (Временные ветки разработки)                   |
|   └── crypto-module (Разработка модуля шифрования)        |
|       ├── Реализация шифрования AES                       |
|       ├── Проверка существования файла                    |
|       └── Проверка входных путей                          |
|                                                           |
├── release/ (Подготовка стабильного релиза)                |
|   └── 1.0.0                                               |
|       ├── Стабилизация и тестирование                     |
|       └── [Слияние] -> main и develop --------------------┘
|
└── hotfix/ (Экстренные исправления ошибок)
    └── 1.0.1
        ├── Исправление обработки ошибок доступа к файлам
        └── [Слияние] -> main и develop
```

## Анализ безопасности

Статический анализ кода рекомендуется выполнять уже на этапе разработки в `feature/crypto-module`.

Основной процесс проверки:

`feature → SAST → develop → интеграционное тестирование → release → финальная проверка безопасности → main`

Это позволяет обнаруживать потенциальные ошибки и уязвимости до попадания изменений в стабильную версию системы.

Для модуля шифрования такая проверка особенно важна, так как ошибки при работе с файлами и криптографическими операциями могут повлиять на сохранность документов.

## Заключение

В ходе работы была практически реализована стратегия ветвления Git Flow для АИС «Цифровой университетский архив».

Для разработки модуля шифрования использовалась отдельная ветка `feature/crypto-module`, после чего функционал был объединен с `develop` и прошел этап интеграционного тестирования.

Для подготовки стабильной версии была создана ветка `release/1.0.0`, а выпущенная версия получила тег `v1.0.0`.

Также был рассмотрен сценарий экстренного исправления ошибки с использованием ветки `hotfix/1.0.1`. После внесения изменений исправление было объединено с `main` и `develop`, а новая версия была отмечена тегом `v1.0.1`.

В результате работы были закреплены практические навыки использования веток `main`, `develop`, `feature`, `release` и `hotfix`, выполнения слияний, создания тегов версий и организации жизненного цикла программного продукта по модели Git Flow.
